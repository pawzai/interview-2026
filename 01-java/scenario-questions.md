# Scenario Questions

Production incidents, architecture exercises and leadership situations - the format that dominates Principal Engineer and Solution Architect loops.

Every scenario uses the **CIDER** structure from [README.md](README.md):

- **Clarify** - what you ask before you answer. Never design or diagnose in silence.
- **Isolate** - narrow the failure domain or the core requirement.
- **Decide** - commit to an approach and name the trade-off.
- **Execute** - the concrete steps.
- **Reflect** - what you monitor, what you would do differently, what you would prevent.

Read the scenario, spend five minutes answering out loud, then compare. The model responses are longer than you should speak - use them as the map, not the script.

---

## Part A - Production incidents

### S1. The service that gets slower every day

> Your Spring Boot service runs fine after a deploy, but response times climb steadily over 3-4 days until it becomes unusable. Restarting fixes it. It is now restarting nightly on a cron job and the team calls that "the fix".

**Clarify.** Does memory usage climb with latency, or is memory flat? Is it all endpoints or a subset? Does throughput stay constant while latency rises? Is the degradation linear or does it accelerate? Was there a deploy that started this, and does it happen in staging?

**Isolate.** The nightly-restart signature points at unbounded growth of something. Four candidate families:

1. **Memory leak** - old-gen occupancy after full GC trending upward, GC frequency and pause time rising. This is the most likely, and the latency is a *symptom* of GC pressure, not of the leak itself.
2. **Connection or thread leak** - Hikari active connections or thread count climbing; eventually every request waits for a connection.
3. **Unbounded collection or cache** - functionally a leak, but with a specific fix.
4. **Fragmentation or native growth** - direct buffers, metaspace from dynamic class generation.

**Decide.** I would confirm which family before touching code, because "it's a leak, add memory" is how teams spend a quarter on the wrong thing. GC logs and JMX metrics tell me this within one cycle.

**Execute.**

1. Pull GC logs and plot post-full-GC old-gen occupancy over the four days. A rising floor is a definitive leak; a flat floor with rising GC frequency is an allocation-rate problem instead.
2. Check thread count, Hikari `active`/`pending`, and file descriptors over the same window.
3. Take heap dumps at day 1 and day 3 from the same instance, and diff them in Eclipse MAT. The dominator tree plus the shortest path to a GC root usually names the class in minutes.
4. Common culprits I check by name: a `static` or `@Component`-scoped `Map` used as a cache with no eviction; `ThreadLocal` values never removed in a pooled thread; listeners or `@EventListener` registrations never deregistered; `ByteBuddy`/CGLIB proxy generation in a loop filling metaspace; a `ScheduledExecutorService` created per request; and Hibernate persistence contexts held open by `open-in-view` on long requests.
5. Fix the specific cause, and add the *general* guard: every cache gets a bounded size and TTL through Caffeine, every `ThreadLocal` a `finally { remove(); }`.

**Reflect.** I would keep the nightly restart until the fix is proven, then remove it deliberately - a scheduled restart masking a leak is technical debt that hides the *next* leak too. Prevention: an alert on post-GC old-gen growth over a 24-hour window, a soak test in the pipeline running load for two hours and asserting flat memory, and JFR always-on so the next occurrence needs no reproduction.

> *Your hook: name the real leak you found - the class, the tool, and the before/after latency.*

### S2. Intermittent 500s under load, nothing in the logs

> During traffic peaks, roughly 2 percent of requests return 500. Application logs show nothing unusual for those requests. The team has been unable to reproduce it in staging.

**Clarify.** Are the 500s returned by the application or generated by the load balancer or ingress? What is the exact status - a 500 from the app looks different in the access log from a 502 or 504 from the proxy. Do the failed requests appear in the application access log at all? Are they concentrated on one endpoint, one instance, or one availability zone? What happens at the same moment to latency, GC, connection pool and CPU throttling?

**Isolate.** "Nothing in the logs" is the most informative detail. If the request never reached the application, the cause is upstream: connection reset during a scale-in or deploy, an idle-timeout mismatch, the accept queue overflowing, or a pod failing readiness while still receiving traffic. If it reached the application but produced no log, the exception is being swallowed - an error path that returns a generic 500 without logging, an `@ExceptionHandler` that logs at DEBUG, or an `OutOfMemoryError` killing the thread before the handler runs.

**Decide.** I would resolve "did the request reach the app" first, because it splits the search space cleanly, and it is answerable from existing access logs in ten minutes.

**Execute.**

1. Correlate by trace ID: does a trace exist for the failed request, and where does it terminate? Tail-based sampling that retains all errors is what makes this instant - if it is not configured, that is the first fix.
2. Check the load balancer's own metrics: `HTTPCode_ELB_5XX` versus `HTTPCode_Target_5XX`, `TargetConnectionErrorCount`, and rejected connections. Non-zero ELB 5XX with zero target 5XX means the app never saw them.
3. If it is the proxy: check that the application's keep-alive idle timeout is *longer* than the load balancer's (the classic race where the server closes a connection the balancer is about to reuse), check `deregistration_delay` against graceful shutdown, verify readiness probes and connection draining, and look at Tomcat's `maxConnections`/`acceptCount` saturation.
4. If it is the application: audit every `catch` block that returns an error response, verify the global `@RestControllerAdvice` logs at ERROR with the stack trace and the trace ID, and check for `Error` (not `Exception`) being thrown - an OOM or `StackOverflowError` bypasses most handlers.
5. Also check the boring causes that produce exactly this pattern: connection pool exhaustion returning a timeout mapped to 500, a downstream circuit breaker with no fallback, and CFS CPU throttling causing probe failures during peaks.

**Reflect.** The underlying defect here is observability, not the 500 itself. I would fix the diagnosis gap permanently: a `@RestControllerAdvice` that guarantees every error is logged once with a trace ID and returned as RFC 9457 `problem+json`, a response header carrying the trace ID, alerting on the 5xx *ratio* rather than count, and a load test in staging shaped like production peak rather than a flat average - the reason it never reproduced is almost certainly that staging traffic has no burstiness.

### S3. The database is on fire after a routine deploy

> Twenty minutes after a deploy, database CPU is at 100 percent, application p99 has gone from 200ms to 8s, and the on-call engineer is asking whether to roll back.

**Clarify (fast - this is an active incident).** What changed in the deploy? Is CPU or IO the constraint? Is it one query dominating, or general load? Did request volume change? Is a migration still running?

**Decide first, diagnose second.** In an active incident with a known recent change, **roll back immediately** and investigate afterwards - unless the deploy included a non-reversible migration, in which case rolling back the code may break against the new schema, which is exactly why migrations must be backward compatible. I would say that explicitly in an interview, because the instinct to keep debugging while users are down is the most common judgement failure at this level.

**Execute (mitigate).**

1. Roll back the application if the schema allows it. Confirm recovery.
2. If rollback is not safe, mitigate directly: `pg_stat_activity` to find the dominant query, `pg_cancel_backend` on the worst offenders, scale up the instance if it buys time, shed load at the edge, and disable the new feature via its flag if there is one.
3. Communicate: status page, stakeholder update, incident channel, and a single incident commander.

**Execute (diagnose).** The usual causes of "routine deploy melts the database":

- A new query with no supporting index - fine on 10k dev rows, sequential scan on 200M production rows.
- An N+1 introduced by a new lazy association or a changed serializer, multiplying query count by the collection size.
- A migration running `CREATE INDEX` without `CONCURRENTLY`, holding a lock while every query queues behind it.
- A connection pool size increase, or more instances, pushing total connections past what the database can schedule.
- A cache accidentally disabled or its key changed, so every request now hits the database.
- An `EXPLAIN` plan flip caused by data growth crossing a planner threshold, coincidentally revealed by the deploy.

I would find it with `pg_stat_statements` ordered by total time, comparing against the pre-deploy baseline.

**Reflect.** Prevention is where I would spend the follow-up: query-count assertions in integration tests so an N+1 fails CI, `EXPLAIN` review for new queries touching large tables as a review checklist item, a migration linter rejecting non-concurrent index creation and blocking DDL, a performance test stage against production-sized data, and canary deployment so the next one hits 5 percent of traffic rather than 100. Also an alert on database CPU and on `pg_stat_statements` regressions that fires before users notice.

> *Your hook: an incident where you were the decision-maker on rollback, and what the postmortem changed.*

### S4. One slow downstream takes down everything

> A third-party API your service calls for enrichment starts responding in 30 seconds instead of 100ms. Within two minutes your entire service is unresponsive, including endpoints that never call that API.

**Clarify.** What is the timeout configured on that client? Is the call synchronous in the request path? Do all endpoints share a thread pool and an HTTP connection pool?

**Isolate.** This is textbook resource exhaustion via a shared pool. Threads handling the slow endpoint occupy every Tomcat worker; unrelated endpoints then queue behind them and time out. The proximate cause is the downstream, but the *design* cause is that a non-critical dependency was allowed to consume a shared, unbounded-in-time resource. Almost always the configured timeout is the default - which for many clients is infinite.

**Decide.** Mitigate now by cutting the dependency out; fix properly by adding isolation so no single dependency can consume the whole service.

**Execute (mitigate).** Disable the enrichment feature via its flag, or deploy a hard timeout, and confirm recovery. If there is no flag, that is finding number one.

**Execute (fix).**

1. **Timeouts on everything** - connect and read - set from the downstream's SLA, not from hope. A timeout longer than your own request deadline is equivalent to no timeout.
2. **Bulkhead**: a dedicated, bounded thread pool or a semaphore per downstream (Resilience4j), so enrichment can consume at most N concurrent slots and the rest of the service is untouched.
3. **Circuit breaker** so repeated slow failures fail fast instead of each one costing a timeout, with a defined fallback - here, return the response without enrichment, because it is non-critical.
4. **Classify the dependency explicitly** as non-critical and make degradation the designed behavior, not an accident.
5. Consider moving enrichment out of the synchronous path entirely - enrich asynchronously and serve the last known value.

**Reflect.** The systemic finding is that no one had enumerated which dependencies are critical. I would produce that list for every service, verify each has a timeout, a bulkhead and a tested fallback, and then *prove* it with fault injection - a chaos experiment that adds 30 seconds of latency to a dependency in staging and asserts the service still serves its core endpoints. Untested fallbacks are the ones that fail. I would also add a dashboard panel per downstream showing latency, error rate and breaker state, because during the next incident the first question will again be "which dependency?".

### S5. Duplicate charges after a retry

> Customers report being charged twice. Investigation shows the payment endpoint was retried by the mobile client after a timeout, and both attempts succeeded.

**Clarify.** Who retried - the client, a load balancer, or an internal retry policy? Did the first request actually succeed, or did it succeed downstream and time out on the way back? How many customers, over what window, and is money still moving?

**Isolate.** The request succeeded at the payment processor but the response was lost, so the client's retry created a second, independent charge. The system has no way to recognize that the second request is the *same logical operation* as the first. This is not a bug in the retry - retries are correct and inevitable - it is a missing idempotency contract.

**Decide.** Stop the bleeding first, reconcile the affected customers, then implement idempotency properly rather than by removing the retry (which would just convert double charges into failed payments).

**Execute (immediate).**

1. Quantify: query for payments with the same customer, amount and a narrow time window, and reconcile against the processor.
2. Refund affected customers proactively, before they ask, and notify them. At this level, saying that unprompted matters - the technical fix is table stakes, the customer handling is judgement.
3. Short-term mitigation: a duplicate-detection guard on (customer, amount, hash) within a few minutes, deployed while the real fix is built.

**Execute (proper fix).** The idempotency key design from [answers.md](answers.md) Q173:

- Client generates an `Idempotency-Key` per logical payment and reuses it on every retry.
- Server inserts the key with a unique constraint **in the same transaction** as the payment, stores the response, and returns the stored response on a duplicate. A concurrent in-flight duplicate gets a 409 rather than proceeding.
- The payment record follows an explicit state machine, with transitions guarded so a double-capture is impossible even if the idempotency layer is bypassed.
- Propagate an idempotency key to the payment processor as well, so the same protection exists on their side.
- Add reconciliation: a scheduled job comparing our ledger against the processor's, alerting on divergence - because the guarantee you do not verify is the one that quietly breaks.

**Reflect.** The deeper lesson is that at-least-once delivery is the default everywhere - HTTP retries, message redelivery, user double-clicks - so idempotency is a design requirement for every non-idempotent operation, not a payments-specific concern. I would audit the other state-changing endpoints for the same gap and add it to the API design checklist and to the code review template.

> *Your hook: a payments or ordering system where you introduced idempotency, with the duplicate rate before and after.*

### S6. Kafka consumer lag growing without bound

> A consumer group's lag has grown to 4 million messages over six hours. Adding instances did not help. The producers are healthy.

**Clarify.** How many partitions does the topic have, and how many consumer instances are in the group? Is lag growing on all partitions or a few? Is the consumer CPU-bound, IO-bound, or idle? Are there frequent rebalances in the logs? Did message volume increase, or did processing slow down?

**Isolate.** "Adding instances did not help" is the key clue and usually means one of three things:

1. **Instances exceed partitions.** Consumer parallelism is capped by partition count - a 12-partition topic gains nothing from the 13th consumer, which sits idle. This is the most common answer.
2. **Skew.** All the traffic is keyed to a few partitions, so one consumer is saturated while others idle. Adding instances cannot help a single hot partition.
3. **Rebalance storm.** Each new instance triggers a rebalance; if processing exceeds `max.poll.interval.ms`, members are evicted and the group rebalances continuously, so it spends its time coordinating rather than consuming.

Otherwise the consumer itself is the bottleneck - a slow downstream call per message, a synchronous database write, or commit-per-message overhead.

**Decide.** Diagnose which of the three before scaling further, because each has a different fix and two of them are made worse by adding instances.

**Execute.**

1. Check per-partition lag. Even lag across partitions with idle consumers means the partition ceiling; uneven lag means skew.
2. Check the consumer group for rebalances (`GroupCoordinator` logs, rebalance rate metric). If it is a rebalance storm: raise `max.poll.interval.ms`, lower `max.poll.records` so a batch finishes within it, enable cooperative rebalancing, and use static group membership.
3. If it is the partition ceiling: increase partitions - accepting the ordering consequence from [answers.md](answers.md) Q176 - or, better if ordering matters, parallelize *within* the consumer by dispatching to a bounded worker pool keyed by the message key, so ordering per key is preserved while throughput scales.
4. If it is skew: change the partitioning key to something higher-cardinality, or shard the hot key with a suffix.
5. If it is per-message cost: batch the downstream writes, remove synchronous calls from the hot path, increase `fetch.min.bytes` and batch size, and stop committing every message.
6. Recovery from 4 million backlog: temporarily scale processing capacity, and consider whether stale messages still need processing at all - for some workloads, seeking to a recent offset and reprocessing the backlog separately is the right call, and knowing when that is acceptable is a business question worth asking.

**Reflect.** Prevention: alert on consumer lag *and* on lag growth rate, so a slow drift is caught before it becomes 4 million; capacity-plan partition count for peak plus headroom at topic creation, since it is one of the hardest things to change later; load test the consumer at 3x expected rate; and track per-message processing time as a first-class metric so the bottleneck is visible without an incident.

### S7. The 3am page you cannot reproduce

> You are paged for elevated error rates. By the time you connect, the metrics are normal. It has happened three times in two weeks, always between 2am and 4am, always self-resolving in under 10 minutes.

**Clarify.** What exactly fires the alert? Do the three occurrences correlate in time of day, day of week, or with any scheduled job? Which errors - the same endpoint, the same exception, the same instance?

**Isolate.** Self-resolving, nocturnal and periodic points strongly at something *scheduled* rather than something traffic-driven. My candidate list:

- A batch job, report generation or ETL competing for the database, or holding a lock.
- Backup or snapshot IO on the database, or a maintenance window.
- Certificate or token refresh failing intermittently.
- Log rotation, or a full disk crossing a threshold.
- A cache expiring in lockstep and causing a stampede against a cold database.
- A partner system's own nightly window, causing timeouts on a downstream call.
- Autoscaling scaling *in* to minimum overnight, so a small burst hits an undersized fleet with cold JVMs.
- A scheduled task running on every instance instead of one, because there is no distributed lock.

**Decide.** The failure here is that the evidence is gone by the time a human looks. My first action is not to guess but to guarantee that the *next* occurrence is fully captured - then the diagnosis is trivial.

**Execute.**

1. Retain the evidence: verify traces for errors are retained by tail-based sampling, JFR is running continuously with a rolling buffer, and thread and heap dumps are triggered automatically on error-rate spikes.
2. Correlate what already exists: overlay the three incident windows against deploy history, cron schedules, database maintenance windows, autoscaling events and GC logs. Three data points at the same time of night usually identifies the job on the first overlay.
3. Ask the boring questions: what runs at 2am, who owns it, and did it start two weeks ago.
4. Once identified, fix the interaction rather than the symptom - move the batch job off the primary, throttle it, add jitter to cache TTLs, hold a floor of instances overnight, or use a distributed lock so the scheduled task runs once.

**Reflect.** Two systemic outputs. First, an alert that pages a human for something that self-resolves in ten minutes and needs no action is a bad alert - it should be a ticket unless customer impact is real, and I would re-derive it from SLO burn rate. Second, "cannot reproduce" is nearly always an evidence-capture problem: I would treat automatic diagnostic capture on anomaly as a platform capability, so the next unexplained event is explained without a second occurrence.

### S8. Deploy succeeded, users see stale data

> After a deploy, some users report seeing old data while others see new. It resolves for individuals after a while but affects a rotating set of users for hours.

**Clarify.** What is behind the inconsistency - a cache, a read replica, a CDN, or multiple application versions running simultaneously? Are the affected users sticky to particular instances? Did the deploy include a data migration?

**Isolate.** A rotating subset with eventual self-correction says the users are hitting *different sources of truth*, and which source depends on routing. Candidates:

- **Read replica lag** - reads routed to a replica behind the primary. Self-corrects as it catches up, affects whoever lands on the lagging replica.
- **Cache with a TTL** - stale entries served until they expire, so the affected set rotates as keys expire. A deploy that changed the data shape without changing the cache key is the classic cause.
- **Local in-memory caches per instance** - instance A has fresh data, instance B stale, and users bounce between them.
- **A partially completed rolling deploy** - two versions live, writing or reading differently.
- **CDN or browser caching** of an API response that should not have been cacheable.

**Decide.** Identify the layer first. I would take one affected user's request and trace it end to end, comparing against an unaffected user's - the divergence point is the answer, and it takes minutes with tracing in place.

**Execute.**

1. Check replica lag metrics and cache hit ratios during the window; check whether the deploy completed on all instances.
2. Mitigate: if it is caching, invalidate the affected key space (having a targeted invalidation capability is itself a design requirement); if it is replica lag, route the affected reads to the primary temporarily.
3. Fix by layer: version the cache key so a deploy naturally invalidates entries whose shape changed; implement read-your-own-writes by routing a user's reads to the primary for a short window after their write (or use a session consistency token); replace per-instance local caches with a shared cache, or accept them only for data where staleness is genuinely harmless; set explicit `Cache-Control` on API responses rather than relying on defaults.

**Reflect.** The design conversation I would open afterwards is that the system had an *undeclared* consistency model - nobody had written down which reads may be stale and by how much. I would document that per endpoint, monitor replication lag with an SLO, and make the staleness window an explicit, tested property rather than an emergent one. And if the business genuinely cannot tolerate staleness for a particular operation, that operation reads from the primary, and we pay for it deliberately.

## Part B - Architecture and system design

Each design below is compressed to the decisions an interviewer is actually grading. Practise by talking through the clarifying questions and the estimate first - candidates who jump to boxes lose points before they draw anything.

### S9. URL shortener at 100 million redirects per day (Q221)

**Clarify.** Read/write ratio? Custom aliases? Expiry? Analytics required, and how real-time? Do URLs need to be unguessable? Global users, or one region?

**Estimate.** 100M redirects/day ≈ 1,160 QPS average, so assume 3-5k QPS peak. Writes are perhaps 1 percent of that - roughly 12 writes/second. So this is an overwhelmingly read-heavy system, and that single ratio drives the whole design. Storage: 1M new URLs/day × 500 bytes ≈ 500 MB/day, under 200 GB/year - small.

**Key decisions.**

- **ID generation.** A counter encoded in base62 gives short, sequential, guessable keys; a random 7-character key (62^7 ≈ 3.5 trillion) is unguessable but needs a collision check. I would use a pre-allocated range per instance (a "ticket server" or Snowflake-style ID) encoded to base62 - no coordination per request, no collision check. If unguessability is required, add random bits rather than switching to pure random.
- **Storage.** The access pattern is a single key lookup, so this is the rare genuine fit for a key-value store - DynamoDB or Redis-backed. Postgres also handles it comfortably at this volume; I would not introduce a new store for 200 GB unless the team already runs one.
- **Cache.** With a Zipfian access distribution, a Redis cache of the hot 1-5 percent absorbs most traffic. Cache-aside with a long TTL, since mappings are immutable once created - which makes invalidation a non-problem, and that immutability is worth stating.
- **Redirect.** 301 is cacheable by the browser (fewer requests, but you lose analytics and cannot change the target); 302 keeps control. I would use 302 with a short cache header, because analytics is usually a requirement.
- **Analytics.** Do not write to the database on the redirect path. Emit an event to Kinesis or Kafka and aggregate asynchronously.

**Scale and failure.** Read path is cache plus CDN, so it scales horizontally trivially. The failure mode that matters: Redis down means every read hits the database at once - so I would use a local Caffeine cache in front of Redis as a second tier, and rate-limit database access on miss. Bad-actor concerns are real here: malicious URLs need a safe-browsing check, and rate limiting per creator prevents abuse.

**What I would deliberately not do.** No sharding at this volume, no multi-region write path unless latency requirements demand it. Stating what you are *not* building, and why, is a principal-level signal.

### S10. Payment processing with strict consistency (Q222)

**Clarify.** Are we the processor or integrating with one? Which currencies and regions, and therefore which regulations? What is the expected volume and the acceptable failure rate? What are the auditability and retention requirements? Do we hold balances (which means a ledger) or just move money?

**Key decisions.**

- **Double-entry ledger, append-only.** Every movement is two balanced entries; balances are derived, never updated in place. This is non-negotiable for auditability, and saying it immediately signals domain knowledge. Corrections are compensating entries, never updates or deletes.
- **Strong consistency inside the boundary.** The ledger lives in a single relational database with ACID transactions - this is where I explicitly refuse eventual consistency. Scale it vertically and by partitioning on account, not by relaxing consistency.
- **Explicit state machine** for the payment: `INITIATED → AUTHORIZED → CAPTURED → SETTLED`, plus `FAILED` and `REFUNDED`, with transitions enforced in the database (a check constraint or a transitions table) so an invalid transition is impossible rather than merely unlikely.
- **Idempotency everywhere** - client to us, us to the processor - per Q173.
- **Outbox** for every event we publish, so notifications and downstream projections can never diverge from the ledger.
- **Reconciliation** as a first-class component: a scheduled job comparing our ledger against the processor's settlement file, alerting on any divergence. Every real payment system has this, and candidates who omit it have not operated one.
- **Saga with orchestration** where multiple services are involved, with compensations that are semantic (a refund, not a rollback).

**Security and compliance.** PCI DSS scope minimization - never store card data, use the processor's tokenization or a hosted field, so card numbers never touch our infrastructure. Encryption at rest and in transit, KMS-managed keys, field-level encryption for anything sensitive that we do hold, immutable audit log of every state change with actor and timestamp, and strict least-privilege access with break-glass procedures.

**Failure modes.** The one to talk about is the ambiguous outcome: we called the processor and did not get a response. We do not know whether the charge happened. The answer is a `PENDING_UNKNOWN` state, a query-by-idempotency-key against the processor to resolve it, a bounded retry with backoff, and a manual review queue for anything unresolved - plus never surfacing an ambiguous state as either success or failure to the user.

### S11. Multi-channel notification service (Q223)

**Clarify.** What volume, and what burst shape - is there a "send to 10 million users" broadcast case? Per-user preferences and quiet hours? Delivery guarantees - at-least-once with duplicates acceptable, or strict? Do we need delivery status tracking? Templating and localization? Regulatory constraints (opt-out, GDPR)?

**Key decisions.**

- **API accepts and returns immediately** with a notification ID; delivery is asynchronous. Never make the caller wait on an SMS gateway.
- **Queue per channel**, because email, SMS and push have wildly different throughput, cost and failure characteristics, and one slow provider must not block the others - bulkheading at the infrastructure level.
- **Provider abstraction with fallback**: an interface per channel with a primary and secondary provider, so a SendGrid outage fails over to SES. This is a common real requirement and a differentiator in the answer.
- **Preference and suppression service** consulted before dispatch - opt-outs, channel preference, quiet hours, and a hard suppression list for bounces and complaints, which is a deliverability requirement for email, not just a nicety.
- **Rate limiting per provider** (they impose quotas) and **per user** (a dedup/frequency cap so a bug cannot send someone 500 emails - this is the failure that actually happens, and designing against it unprompted scores well).
- **Templating** versioned and stored centrally, rendered at send time with localization.
- **Idempotency** on the inbound request, and a dedup key on the dispatch so a redelivered message does not send twice.
- **Status tracking** via provider webhooks into a delivery-status store, with the notification lifecycle (`QUEUED → SENT → DELIVERED → OPENED / BOUNCED / FAILED`) queryable.

**Retries.** Exponential backoff with jitter, a bounded attempt count, and a DLQ per channel. Distinguish retryable (5xx, timeout, throttle) from permanent (invalid address, unsubscribed) - retrying a hard bounce damages sender reputation.

**Scale.** For a 10M broadcast, fan out through a batch job that writes to the queue in chunks rather than one giant transaction, and spread the send over a window to respect provider rate limits and to avoid a thundering herd on your own systems when everyone clicks the link at once.

### S12. Distributed rate limiter across 200 instances (Q224)

**Clarify.** What is being limited - per API key, per user, per IP, per endpoint? What limits and windows? Is it a hard limit (billing/quota) or a protective one? What is the acceptable error - can we allow 10 percent over? What happens if the coordination store is unavailable?

**That last question is the design fork**, and asking it is the point of the exercise.

**Key decisions.**

- **Algorithm**: token bucket, for burst tolerance with a sustained rate.
- **Coordination**: Redis with an atomic Lua script implementing the bucket - a single round trip, no race between check and decrement. `INCR` with `EXPIRE` is the naive version and has a race plus the fixed-window boundary burst; the Lua script or Redis Cell module avoids both.
- **Latency**: a Redis call per request adds ~1ms, which is acceptable at the edge but not for every internal hop. For very high volume, use **local token buckets with periodic global reconciliation**: each instance holds a share of the quota, and rebalances every second or two. Approximate, much faster, and adequate for protective limits - not for billing.
- **Failure mode, stated explicitly**: fail *open* for protective limits (availability matters more than perfect enforcement) and fail *closed* for quota or billing limits. Decide it deliberately and document it.
- **Hot keys**: one very large customer concentrated on one Redis key is a hotspot; shard the key or move that tenant to dedicated capacity.

**Response contract.** 429 with `Retry-After`, plus `X-RateLimit-Limit`, `-Remaining` and `-Reset` so well-behaved clients self-throttle rather than hammering. Rate limiting that clients cannot observe just produces retry storms.

**Where to enforce.** At the edge for coarse protection (API Gateway or ingress, keeping abusive traffic off your compute entirely) and in the application for anything needing business context. Both, not either.

### S13. Tamper-evident audit log over five years (Q225)

**Clarify.** What must be auditable - all data changes, or specific regulated events? Who queries it, how often, and by what dimensions? What is the retention and legal hold requirement? Does tamper-evidence need to be cryptographic and externally verifiable, or is restricted access sufficient? Volume per day?

**Key decisions.**

- **Append-only, no update or delete path** - enforced at the database level with permissions, not just by convention. The application's credentials have `INSERT` and `SELECT` only.
- **Hash chaining** for tamper evidence: each record includes the hash of the previous record, so any modification breaks the chain from that point. Periodically publish the chain head somewhere independent (a separate account, a WORM bucket, or a signed external notarization) so an attacker with full database access still cannot rewrite history undetected. This is the core of the answer - restricted access alone is not tamper evidence, it is tamper *hope*.
- **Write path decoupled** from the business transaction only if loss is acceptable - which for audit it usually is not, so the audit write goes in the same transaction (or via the outbox) and the business operation fails if the audit write fails. Say that trade-off out loud: correctness over availability, deliberately.
- **Storage tiering** for five years: hot data (90 days) in Postgres or OpenSearch for interactive query; warm and cold in S3 as partitioned Parquet with Athena or Glue over it, with lifecycle transitions to Glacier. **S3 Object Lock in compliance mode** gives genuine WORM guarantees that even a root user cannot override, which is what regulators actually ask for.
- **Partitioning by time** so retention is a partition drop rather than a mass delete, and queries prune efficiently.
- **What is recorded**: who (authenticated principal, not a service account), what (entity, before and after, or a diff), when (server time, with the trace ID), where (source IP, client), and why (business operation), plus the schema version so five-year-old records remain interpretable.

**The tension to name.** GDPR erasure versus immutable audit. Resolution: store PII by reference (a pseudonymous subject ID) so erasure can remove the mapping while leaving the audit chain intact, or use crypto-shredding - encrypt per-subject and destroy the key. Raising this unprompted is a strong signal.

### S14. Real-time dashboard over 100k events/second (Q226)

**Clarify.** What latency does "real-time" mean - one second, or one minute? How many concurrent dashboard viewers? What aggregations, over what time windows? Is exact accuracy required, or are approximations acceptable? How long must the raw data be retained?

**Estimate.** 100k events/second at ~1 KB is 100 MB/s, 8.6 TB/day raw. That number alone tells you raw storage is a cost problem and that you cannot query raw data interactively.

**Key decisions.**

- **Ingest** through Kafka or Kinesis, partitioned by a high-cardinality key. At 100k/s, partition count and producer batching are the throughput levers.
- **Pre-aggregate in a stream processor** (Flink, Kafka Streams) into tumbling and sliding windows - this is the central decision. You cannot aggregate 8.6 TB/day at query time for a dashboard, so the dashboard reads pre-computed rollups at one-second, one-minute and one-hour granularity. Handle late-arriving events with watermarks and a defined allowed lateness, and state what happens to data arriving after that.
- **Serving store**: a time-series or OLAP store built for this - ClickHouse, Druid or Pinot for sub-second queries over rollups; Timestream or Prometheus for simpler metric shapes. A relational database is the wrong tool here and saying so with a reason is the point.
- **Approximations where they buy orders of magnitude**: HyperLogLog for distinct counts, t-digest for quantiles. Exact distinct counts over a billion events are enormously more expensive, and the dashboard user cannot tell the difference - but ask first, because for billing they can.
- **Push to the browser** via SSE or WebSocket from a fan-out layer, with server-side throttling - a dashboard updating 100 times a second is useless to a human, so coalesce to once or twice a second. With many viewers, one subscription per query result fanned out to all viewers, not one query per viewer.
- **Raw retention** to S3 in Parquet for replay and ad-hoc analysis, with lifecycle expiry.

**Failure modes.** Backpressure when the processor cannot keep up - the stream buffers, so lag is your primary alert, and you need a documented behavior for a large backlog (catch up, or skip to head and backfill separately). A stream processor restart must resume from checkpointed state, so checkpoint configuration and state store sizing are operational essentials, not details.

### S15. Monolith to services without a big bang (Q227)

**Clarify.** What is actually driving this - deployment velocity, scaling, team autonomy, or reliability? (If nobody can answer, the correct recommendation may be *do not do this*, and saying so is a principal-level answer.) How large is the codebase and the team? What is the release cadence today, and what is the constraint on it? Is the database shared, and how entangled is it?

**Approach.**

1. **Establish the why and the success metric** first - "deploy independently, from monthly to daily" or "scale the pricing engine separately" - so extraction stops when the goal is met rather than continuing until everything is a service.
2. **Modularize in place before extracting.** Enforce module boundaries inside the monolith with package structure, ArchUnit tests and internal APIs. This is cheap, reversible, and delivers much of the benefit; it also reveals which seams are real. Many organizations should stop here.
3. **Strangler fig** for extraction: put a facade or gateway in front, route one capability at a time to the new service, and retire the old code path once traffic is fully shifted. Never a parallel rewrite.
4. **Choose the first service deliberately**: something with a clear boundary, meaningful business value, and low coupling - not the hardest and not the most trivial. It is a learning vehicle for the platform work (CI/CD, observability, on-call) as much as a technical change.
5. **Split the data last and explicitly.** The database is the hard part. Sequence: stop cross-module joins in code, move to an API call, then separate the schema, then the instance. Where both sides need the data, use change data capture or events to maintain a read model rather than a shared table.
6. **Keep both paths live** behind a feature flag with dual-run and comparison (shadow traffic to the new service, compare outputs, do not serve them) until confidence is high. This is what makes it genuinely non-big-bang.
7. **Invest in the platform in parallel** - pipelines, tracing, service templates - because extraction without it produces a distributed monolith that is worse than what you started with.

**Reflect.** The failure mode I would call out: extracting services while the shared database remains, producing services that must deploy together and cannot fail independently. That is all of the cost and none of the benefit, and it is the most common outcome of these programmes. I would define a checkpoint after the second service to honestly reassess whether the metric is moving.

> *Your hook: a migration you led - the driver, the sequencing, the metric that improved, and what you would sequence differently.*

### S16. Hybrid keyword and semantic document search (Q228)

**Clarify.** Corpus size and growth? Document types and structure? Query latency requirement? Are results access-controlled per user, and is the control per document or per section? How fresh must the index be after a document changes? Is this a search box, or the retrieval half of a RAG feature?

**Key decisions.**

- **Hybrid retrieval, not either alone.** BM25 catches exact terms, product codes, names and negation, which dense vectors handle poorly; embeddings catch paraphrase and intent, which BM25 misses. Run both and fuse with reciprocal rank fusion. This is the answer, and knowing *why* each fails alone is the substance.
- **Rerank** the fused top ~50 with a cross-encoder down to the top 5-10. This is usually the single largest quality gain per unit of effort, at the cost of latency - so it is applied to a small candidate set, never the whole corpus.
- **Chunking** per Q213: structure-aware, 200-500 tokens with overlap, metadata attached, small-to-big retrieval where the matched chunk brings its parent section along.
- **Access control at query time**, as a pre-filter on the vector and lexical queries - never post-filtering, which both leaks (via result counts and latency) and breaks top-k. In a multi-tenant system this is a security control, not a feature.
- **Store**: OpenSearch handles both lexical and vector in one system, which avoids operating two stores and keeps fusion simple; pgvector plus Postgres full-text is a good choice when the corpus is moderate and Postgres is already there. A dedicated vector database earns its place at large scale or with demanding filtering.
- **Indexing pipeline**: change detection, extraction (PDF, HTML, Office), chunking, embedding, and upsert - idempotent and resumable, with the embedding model version stored per vector so a model change triggers a controlled re-index rather than a silently mixed index.

**Evaluation.** A labelled query set with recall@k and NDCG, run in CI on any change to chunking, model or fusion weights. Without it, tuning search is guesswork - and search quality regressions are invisible until users complain.

### S17. Multi-tenant SaaS with isolation and noisy neighbours (Q229)

**Clarify.** How many tenants, and what is the size distribution - a long tail of small tenants plus a few enormous ones changes everything. What are the compliance and data residency requirements? Is per-tenant customization required? What is the pricing model, since it determines whether per-tenant cost attribution is needed?

**Key decisions.**

- **Isolation model**, the central choice: shared database with a tenant column (cheapest, densest, highest blast radius from a bug); schema per tenant (better isolation, migration complexity grows with tenant count); database per tenant (strongest isolation and easiest per-tenant restore and residency, most expensive and operationally heaviest). My usual recommendation is a **tiered** model - pooled for the long tail, dedicated for enterprise and regulated tenants - which matches cost to willingness to pay and is what most mature SaaS converges on.
- **Enforce isolation at the lowest layer possible** per Q144: Postgres row-level security or a global Hibernate filter, so a developer who forgets the predicate still cannot leak. Tenant identity comes from the token, never from a request parameter.
- **Tenant in everything**: cache keys, queue messages, log lines, metrics labels, trace attributes, S3 prefixes, and file names. Every one of these has been a real leak in some product.
- **Noisy neighbours**: per-tenant rate limits and quotas; bounded concurrency per tenant so one cannot consume the whole pool; separate queues or priority lanes for large tenants; connection pool partitioning; and query cost limits (statement timeouts) so one tenant's expensive query cannot saturate the database. Detect it with per-tenant metrics - without per-tenant instrumentation, noisy-neighbour incidents are undiagnosable.
- **Onboarding and offboarding as automated flows**, including provisioning, migration and complete deletion, because manual tenant management does not survive growth and GDPR erasure has a deadline.
- **Migrations across thousands of tenants**: a controlled rollout with per-tenant progress tracking and the ability to pause, not a single script.

**Cost.** Per-tenant cost attribution through tagging and metrics, because at some point someone will ask which customers are unprofitable, and being able to answer changes the business conversation.

### S18. Feature flag and experimentation platform (Q230)

**Clarify.** Is this flags only, or A/B experiments with statistical analysis? How many flags and evaluations per second? Is evaluation server-side, client-side, or both? Do we need targeting rules by user attribute? Who changes flags - engineers only, or product managers? Is buy-versus-build on the table (it usually should be)?

**A principal-level answer starts by questioning the build.** LaunchDarkly, Unleash and similar are mature and cheap relative to engineering time, so I would want a specific reason to build - data residency, extreme scale, or deep integration. Saying that first, then designing anyway, is the right order.

**Key decisions.**

- **Evaluation happens locally, in-process.** The SDK holds the full ruleset in memory and evaluates with zero network calls, so a flag check is nanoseconds and the platform being down cannot break the application. Rules are pushed via SSE or streaming, with polling as a fallback and a bundled default so a cold start with no connectivity still works. This is the single most important design property, and candidates who put a network call in the evaluation path have designed an outage.
- **Deterministic bucketing**: `hash(flagKey + userId) % 100` so the same user always gets the same variant across services and sessions, without coordination. Including the flag key means a user is not correlated across experiments.
- **Targeting rules**: percentage rollout, attribute-based segments, individual overrides, and a kill switch that bypasses everything.
- **Events for analysis**: emit an exposure event on evaluation (sampled, because at high volume this is the expensive part) joined against outcome metrics for experiment analysis.
- **Statistics done properly** if experiments are in scope: pre-registered metrics and minimum detectable effect, sample size calculation, sequential testing or a fixed horizon to avoid peeking, guardrail metrics that stop a harmful experiment automatically, and a stated approach to multiple comparisons. Getting this wrong produces confident wrong decisions, which is worse than no experimentation.
- **Governance**: audit log of every flag change with actor and reason, approval for production-critical flags, an owner and expiry date per flag, and automated nagging for stale flags. Flag debt is the real long-term cost - a codebase with 400 permanent flags has 2^400 configurations and no one can reason about it.

**Failure modes.** Default values must be safe (the flag off, the old behavior); a corrupt ruleset must not be applied; and flag evaluation must never throw. The platform is in the critical path of every service, so it needs a higher availability target than its consumers - or, better, an architecture where its unavailability is invisible, which is what local evaluation buys.

## Part C - Leadership and behavioral scenarios

Answer these with STAR-L (Situation, Task, Action, Result, Learning) in two to three minutes. The model responses give the *shape* and the judgement being assessed - fill them with real events from Nittany Technologies, Verizon India and Sonata Software.

### S19. Two senior engineers deadlocked on an architectural decision

> Two of your strongest engineers have been arguing for three weeks about whether to use Kafka or SQS for a new integration. The team is blocked and morale is dropping.

**What is being assessed:** whether you can unblock without either steamrolling or abdicating.

**Approach.** First, separate the technical disagreement from the interpersonal one - three weeks means it has stopped being about the technology. I would talk to each privately to understand what they actually care about, which is often "I do not want to be responsible for operating Kafka" or "my previous team got burned by SQS ordering".

Then I would make the decision *criteria-driven* rather than preference-driven: write down the requirements that discriminate between the options - do we need replay, do we need ordering, what is the volume, what does the team operate today, what is the cost - and have both engineers evaluate against them jointly. Very often the criteria collapse the argument, because one option obviously fails a hard requirement that nobody had written down.

If they remain genuinely equivalent, that is important information: when two options are equivalent, the choice does not matter much, and the cost of continued debate exceeds the cost of choosing wrong. I would then decide, explain the reasoning, document it as an ADR including the rejected option and why, and set a review trigger ("if we need replay within six months, we revisit"). I would ask the engineer whose option was not chosen to own the implementation, if they are willing - it signals the decision was about the problem, not about winning.

**Learning to state.** Three weeks of block is a process failure I own, not theirs. I would introduce a lightweight rule: a technical debate that is not resolved within a week is escalated for a decision, with the decision recorded. Reversible decisions get decided fast; only genuinely irreversible ones earn extended analysis.

### S20. You inherit a team with no tests and a 6-week release cycle

> You join as tech lead. The codebase has 4 percent coverage, releases take a weekend and often roll back, and the team believes this is normal.

**Approach.** I would resist the instinct to announce a testing initiative in week one. First, spend two to three weeks understanding *why* - usually the code is untestable rather than the team being careless, and telling experienced engineers to "write more tests" without changing that is both insulting and ineffective.

Then I would find a metric the business already cares about - failed releases, weekend hours, incident rate - and connect the technical work to it, because "increase coverage to 80 percent" gets deprioritized while "stop losing weekends" does not.

Sequence I would follow: build a characterization test harness around the highest-risk area first, so change becomes safe before it becomes clean; add tests to every change going forward (the "boy scout" rule enforced in review, not as a mandate); pick one painful release step and automate it each cycle rather than proposing a big-bang pipeline; and make the improvement visible - a chart of release duration on the wall does more than any number of advocacy meetings.

I would deliberately *not* set a coverage target early. Coverage as a goal produces assertion-free tests. I would measure what matters: change failure rate and lead time.

**Learning.** The cultural change matters more than the technical one, and it comes from the team experiencing a safe release, not from being told it is possible. My job is to engineer the first one.

### S21. A junior engineer is repeatedly missing estimates

> An engineer two years into their career has missed the last four sprint commitments, each time reporting "almost done" until the final day.

**Approach.** I would start from the assumption that this is a systems or support problem rather than a capability or character problem, because that is usually true and because starting from blame guarantees I get bad information.

In a private, low-stakes conversation I would ask what the work actually looked like, not why it was late. Common causes: the task was larger or vaguer than it appeared and they did not feel safe saying so; they are blocked and afraid to ask; they are being interrupted; the estimate was made by someone else; or they do not know how to break work down, which is a teachable skill rather than a flaw.

Actions depending on the cause: pair on decomposition until they can do it themselves; establish a norm that raising a blocker within a day is *expected* behavior and praise it publicly when it happens; make progress visible through smaller pull requests so "almost done" is observable rather than self-reported; and check whether the psychological safety issue is broader than one person, because if they are afraid to say they are stuck, others probably are too.

I would also check my own contribution: did I make it safe to report bad news, or did the team see someone punished for it?

**Learning.** Repeated "almost done" is nearly always a signal about the environment, not the individual. Fixing the individual without fixing the environment produces the same problem in the next person.

### S22. The business wants a date you know is unrealistic

> A stakeholder has committed publicly to a launch date. Your assessment is that the scope requires twice the time. They ask you to "find a way".

**Approach.** I would not say yes, and I would not say no. Both are failures - the first is dishonest and the second is unhelpful.

Instead I would make the trade-off explicit and hand the decision back with options: what can be delivered by the date at full quality (a reduced scope), what the full scope would cost in time, and what a date-driven full-scope delivery would actually mean - which I would state concretely rather than as "technical debt": no automated tests on the new paths, manual deployment, no monitoring, and a likely production incident in the first month with a named cost.

I would bring evidence rather than intuition - past delivery data, a decomposed estimate with the uncertain items identified - because "trust me" does not survive contact with a public commitment.

I would also look for the third option, which usually exists: launch to a limited segment, launch behind a flag with a phased rollout, deliver the highest-value slice and follow with the rest, or buy instead of build for one component. Being the person who finds the option nobody had considered is more valuable than being the person who was right about the date.

If the decision is still to proceed as committed, I would commit to it, document the accepted risks and the remediation plan in writing so it is a shared decision rather than an engineering failure, and negotiate the follow-up time *before* the launch, not after - because after the launch there is always another date.

**Learning.** The failure was upstream: engineering was not in the room when the commitment was made. I would work to change that, since fixing the process is the only durable answer.

### S23. You made a costly wrong decision

> Describe a technical decision you made that turned out badly.

**What is being assessed:** intellectual honesty, and whether you learn systematically or just feel bad.

**Shape of a strong answer.** Choose a decision that was genuinely yours, genuinely wrong, and genuinely costly - not a disguised humblebrag ("I was too thorough"). Explain what you knew at the time and why the decision was reasonable given that information, because a decision that was obviously wrong at the time shows poor judgement, while one that was reasonable but wrong shows a learning opportunity.

Then: how you discovered it, how quickly you acknowledged it publicly, what it cost in concrete terms, what you did to recover, and - most importantly - what you changed *structurally* so the class of error is less likely. "I am more careful now" is a weak answer; "we now require a reversibility assessment and a defined kill criterion for any architectural decision" is a strong one.

Candidates at 19 years should have a real one ready. Not having one signals either a lack of ownership or a lack of candour, and interviewers read it that way.

### S24. Your first 90 days

> What would you do in your first 90 days here?

**Shape.** Resist the urge to promise a transformation. The strongest version of this answer is weighted heavily toward learning.

- **Days 1-30 - understand.** Meet everyone I will work with and ask what is working, what is painful and what they would change. Read the code, the incidents, the postmortems, the architecture decisions and the roadmap. Ship something small and real in week one or two - a bug fix or a small improvement - to learn the whole delivery pipeline from the inside and to establish that I do the work. Explicitly change nothing structural.
- **Days 30-60 - contribute and form a view.** Take on meaningful delivery, participate in on-call, and start forming a written assessment of the top three technical risks and the top three opportunities, validated against what the team told me rather than what I assumed on day one.
- **Days 60-90 - propose and start.** Share the assessment with the team and with leadership, get it challenged, and begin the highest-value item with a measurable outcome attached. Also establish the durable practices I care about - design review, ADRs, postmortem quality - by demonstrating them rather than mandating them.

Throughout: build credibility by helping people rather than by critiquing decisions made before I arrived. The fastest way for a senior hire to fail is to arrive with answers.

**The line worth saying:** at nineteen years in, I have learned that the thing that looks obviously wrong on day three is usually a rational response to a constraint I have not discovered yet. So I would spend the first month finding the constraints.

### S25. Positioning the .NET to Java transition

> You spent nine years in .NET before moving to Java. How do you present that?

**Frame it as an asset, specifically.** The claim to make: having built the same architectural patterns in two independent ecosystems, I can distinguish what is essential from what is framework accident. Dependency injection, ORM behavior, async models, security filters and layered architecture exist in both; the .NET and Java implementations differ in surface and idiom, and having seen both makes me faster at evaluating a *third* thing - which is what adopting new technology actually requires.

**Be concrete rather than abstract.** Name the transfers: Entity Framework's change tracking and lazy loading map directly onto Hibernate's persistence context, including the same N+1 and detached-entity traps; ASP.NET middleware pipelines map onto the Spring Security filter chain; `async`/`await` and `Task` map onto `CompletableFuture` and now virtual threads, and knowing the .NET model made the JVM's threading trade-offs easier to reason about, not harder.

**Address the concern behind the question.** The interviewer wants to know if you are a shallow generalist. Counter it with depth: pick one Java-specific area - the memory model, GC tuning, the Spring proxy mechanics - and go deeper than a single-ecosystem engineer would expect. Depth in one place buys credibility for the breadth everywhere else.

**And name the learning.** Moving stacks mid-career at ten years in required deliberately becoming a beginner again, which is uncomfortable and is exactly the skill the industry now demands every few years. That is the real answer to "how do you keep learning at nineteen years" - I have already done it once, at scale, in production.

## Practice protocol

Do not read these passively. For each scenario:

1. Set a timer for five minutes and answer out loud, recording yourself.
2. Write the clarifying questions *before* looking at the model answer - this is the habit most senior candidates lack.
3. Compare, and note only the points you missed. Add them to a personal gap list.
4. Re-attempt the ones you missed a week later.

Target: two production incidents and one system design per day for two weeks, then a full mock covering one of each in 60 minutes.
