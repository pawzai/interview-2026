# Microservices Cheatsheet

Fast revision. Read the night before and again 30 minutes before. Everything here is expanded in [answers.md](answers.md); the question numbers are the index.

---

## The five sentences

1. **You cannot distinguish slow from dead.** Timeouts, retries, breakers, health checks and consensus all exist because of this one fact.
2. **Every write crossing a boundary is at-least-once.** Exactly-once delivery does not exist; exactly-once *effect* is built by the consumer.
3. **Coupling moves, it does not disappear.** Splitting converts compile-time coupling into runtime, schema and temporal coupling.
4. **The failure mode is amplification, not the original fault.** The question is never "what broke" but "why did it stay broken".
5. **A timeout means unknown, not failed.** Never compensate or fail over on an ambiguous result without asking.

## CAP, PACELC, consistency

**CAP**: under a **P**artition, choose **A**vailability or **C**onsistency (linearizability).
**PACELC**: **P**artition → **A**/**C**; **E**lse → **L**atency/**C**onsistency. The else-case is the one you face every day.

**C in CAP** = linearizability (replication). **C in ACID** = integrity constraints (application). Unrelated (Q63).

| Model | Violation looks like |
| --- | --- |
| Linearizable | Two users see different balances at the same instant |
| Sequential | Real-time ordering not preserved across processes |
| Causal | Reply appears before the comment |
| Read-your-writes | You save, reload, and see the old value |
| Monotonic reads | Refresh shows an item, then not, then yes |
| Eventual | Any of the above, until convergence |

**Session guarantees are cheap and remove most user-visible weirdness.** Aim for causal + session; reserve linearizability for one or two entities (Q62).

## Delivery semantics

| Semantics | Achieved by | Burden |
| --- | --- | --- |
| At-most-once | Ack before processing | Application tolerates loss |
| **At-least-once** | Ack after processing | **Consumer must be idempotent** |
| Effectively-once | At-least-once + dedup/transactional state | Consumer, via inbox or natural idempotency |

**Kafka EOS is exactly-once between Kafka topics only.** The moment a database is involved, you are back to at-least-once + idempotency (Q44).

**Exactly-once effect = two local transactions**: outbox (producer) + inbox (consumer). No coordination required (Q93).

## Saga versus 2PC

| | 2PC / XA | Saga |
| --- | --- | --- |
| Atomicity | Real | Eventual (all done, or all compensated) |
| Isolation | Yes | **None** - intermediate states are visible |
| Availability | Product of all participants × coordinator | Each participant independent |
| Blocking | Coordinator crash blocks with locks held | No blocking |
| Works across | XA-capable resources only | Anything |
| Use when | One service, one host, two resources | Across services |

**Saga step types** (Q85):

```
compensatable ... compensatable | PIVOT | retriable ... retriable
        (failure → unwind)              (failure → keep trying)
```

**Push the pivot as late as possible.** Every step must be one of the three; a step that is neither compensatable nor retriable is a design defect.

**Choreography ≤ 3 participants, linear, no branching. Otherwise orchestrate.** Choreography's cost: the workflow exists nowhere (Q86).

**Saga isolation countermeasures** (Q89): semantic lock, commutative updates, pessimistic view (reorder steps), reread value, version file, by value.

## Idempotency

| Element | Rule |
| --- | --- |
| Key generated by | **The client, before the first attempt**, reused across retries |
| Storage key | `(client/tenant, idempotency_key)` |
| Stored | Status, request-body hash, full original response, resource ID, expiry |
| Retention | Longer than every retry/redelivery window. 24h minimum, 7-30 days for money |
| Replay returns | **The original response**, original status code, plus a replay header |
| Same key, different body | **Reject** 422/409 (Q95) |
| Concurrent duplicates | **`INSERT` with a unique constraint first** - claim, then work (Q97) |
| In progress | 409 + `Retry-After`, never "success" |

**Make `balance += 10` idempotent**: append a ledger row with a unique constraint on the operation ID and derive the balance. Give the operation an identity (Q96).

## Outbox versus CDC

| | Polling relay | CDC (Debezium) |
| --- | --- | --- |
| Latency | 100ms-1s | < 100ms |
| DB load | Query + UPDATE per row | Reads WAL only |
| Ordering | Needs care (commit-visibility gap) | **Commit order by construction** |
| Ops burden | Application code only | Connect/Debezium, slots, offsets |
| Worst failure | Lag grows visibly | **Replication slot fills the WAL disk → source DB down** |
| Cleanup | Must prune | Delete the row in the same transaction |

**Default: polling.** Move to CDC for measured DB load, sub-second latency, or high-throughput ordering.

**Both are at-least-once**, because publish and mark-published cannot be atomic. Publish-then-mark (duplicates) is always correct; mark-then-publish (loss) never is (Q91).

**Use CDC on the outbox table, not on domain tables** - otherwise you have published your internal schema (Q92).

## Kafka essentials

| Setting | Purpose |
| --- | --- |
| `enable.idempotence=true` | Producer dedup per partition; preserves order under retry |
| `acks=all` + `min.insync.replicas=2` + RF 3 | No acknowledged write lost with one broker down |
| `unclean.leader.election.enable=false` | Prevents silent truncation of acknowledged data |
| `max.poll.records` | **The one that is usually wrong** when rebalances storm (Q47) |
| `max.poll.interval.ms` | Liveness vs tolerance dial - not the heartbeat |
| `CooperativeStickyAssignor` | Incremental rebalance, no stop-the-world |
| `group.instance.id` | Static membership - no rebalance on rolling restart |

**Ordering**: only within a partition. Retries, retry topics and DLQs all break it. **You can have ordering or non-blocking error handling, not both** (Q48).

**Hot key with ordering** (Q49): key-based worker dispatch inside the consumer (best), or a finer composite key, or drop the ordering requirement via version checks. More partitions does *not* help.

**Lag**: alert on **max per partition, measured in seconds**, plus lag derivative, plus zero-consumption-with-lag. Aggregate offset lag hides a single stuck partition (Q53).

**Schema registry**: `FULL_TRANSITIVE` for a topic with many independent consumers and replay. Permits only adding/removing optional fields with defaults (Q54).

**Compatible ≠ correct.** A default value satisfies the registry and can still be wrong (Q55).

## Timeouts, retries, breakers

**Timeout hierarchy rule**: the caller's timeout must be **shorter** than the callee's, strictly decreasing down the chain. Better still, **propagate a deadline** (Q104).

```
edge 3000ms → A 2500ms → B 2000ms → C 1500ms
```

**Retry amplification** = product of per-layer attempts. 3 × 3 × 3 = **27×**.
**Retry budget** = cap retries at 10-20% of *successful* traffic. Under a broad outage the budget collapses to ~0, so amplification → 1× exactly when it matters (Q106).

**Full jitter**: `sleep = random(0, min(cap, base × 2^n))`. Deterministic backoff *creates* synchronization (Q105).

**Retry safe**: 408, 429, 502, 503, 504, connection failures before send.
**Never**: 400, 401, 403, 404, 422.
**Ambiguous**: 500 and any timeout - retry only with an idempotency key.

**Circuit breaker** (Q107):

| Setting | Note |
| --- | --- |
| Failure rate over a **sliding window** | Not consecutive failures |
| **Minimum number of calls** | Most-missed setting; without it, 1-of-1 opens the circuit |
| **Slow-call rate + duration** | A slow-but-succeeding dependency never trips a plain breaker (Q108) |
| `recordExceptions` / `ignoreExceptions` | A 400 is not a downstream failure |
| Half-open permitted calls | Small (3-10), with exponential wait-duration backoff |

**Bulkhead sizing**: `threads = throughput × p99 latency` (Little's Law), plus 20-50% headroom, capped below what saturates the downstream.

**Rate limiting** = client policy, at the edge. **Load shedding** = server reaction, at the service. **Backpressure** = signal upstream, between stages. Three different things (Q110).

**Metastable failure**: the trigger is gone and the system stays down because retries / expired queued work / cold caches now *are* the load. Fix: shed hard, drain expired work, stop retries, warm caches, ramp back (Q112).

## Health checks and shutdown

- **Liveness** → restart me. In-process only.
- **Readiness** → stop sending traffic. **Instance-local facts only.**
- **Startup** → suspend the other two during boot.

**Readiness must never check a shared dependency.** All instances fail together → zero backends → total outage from a 20-second blip (Q117).

**Graceful shutdown order** (Q118):

1. SIGTERM
2. Fail readiness, **keep serving**
3. **Sleep for LB propagation** (5-15s) ← the step everyone omits
4. Stop accepting new HTTP + pause the consumer
5. Finish in-flight work
6. Commit offsets, leave the consumer group cleanly
7. Flush outbox batch, metrics, traces
8. Close pools, exit 0

## Latency arithmetic

**Parallel fan-out**: N calls each at p99 → aggregate p99 = individual **p99^(1/N)**.
Five calls at p99 100ms → **4.9% exceed 100ms**; aggregate p99 ≈ single-service p99.8 (Q187).

**Little's Law**: `concurrency = throughput × latency`.
- Thread pool: 500 rps × 0.04s = 20 threads (size at p95, not the mean).
- Queue latency: `depth / throughput`. 1,000 deep at 500 rps = **2 seconds added**. Size queues in latency, not depth.

**USL**: `C(N) = N / (1 + α(N−1) + βN(N−1))`. The **coherency** term β is quadratic, so the curve **turns over** - more nodes can mean less throughput. Amdahl only plateaus (Q190).

**Percentiles do not average.** Aggregate the histogram buckets (additive) and compute the quantile once (Q148).

## Observability

| Signal | Best at | Wrong for |
| --- | --- | --- |
| Metrics | Is something wrong, how bad | Why *this* request was slow |
| Logs | What happened in one execution | Aggregate trends |
| Traces | Where the time went, causal path | Detection (they are sampled) |
| Profiles | Which code used the resource | Anything cross-service |

`traceparent: 00-<32 hex trace-id>-<16 hex span-id>-<flags>`

**Sampling**: head-based cannot sample on outcome. **Tail-based** keeps 100% of errors and slow traces + 1% baseline. Compute SLI metrics on **100% of requests, before sampling** (Q141, Q142).

**Links, not parent-child**, when the parent does not wait: async consumption, batch of N traces, scheduled jobs (Q143).

**Cardinality**: one `user_id` label × 1M users × 20 endpoints × 5 statuses = 100M series. Bucket, allowlist the top N, or move it to logs/traces (Q144).

**Context is lost at**: thread pools (wrap the executor, clear in `finally`), message boundaries (inject into headers - **including the outbox row**), scheduled jobs (new root + links) (Q140).

## SLO and error budget arithmetic

| SLO | Downtime / 30 days | / week |
| --- | --- | --- |
| 99% | 7.2 hours | 1.7 h |
| 99.9% | **43.2 minutes** | 10.1 min |
| 99.95% | 21.6 minutes | 5 min |
| 99.99% | 4.3 minutes | 1 min |

**Multi-window multi-burn-rate** (Q150):

| Burn rate | Long / short window | Budget used | Action |
| --- | --- | --- | --- |
| 14.4 | 1h / 5m | 2% | Page |
| 6 | 6h / 30m | 5% | Page |
| 3 | 1d / 2h | 10% | Ticket |
| 1 | 3d / 6h | 10% | Ticket |

Long window = significance. Short window = still happening. Both must hold.

**Error budget policy**: >50% free → ship freely. <25% → owner sign-off, reliability prioritized. Exhausted → **feature freeze on that service**, mandatory postmortem, named reliability allocation. Needs written business agreement and a documented exception path (Q120).

## Deployment and release

**Deployment ≠ release.** Separating them makes rollback a config change, shrinks blast radius, and enables trunk-based development (Q171).

| Strategy | Rollback | Schema constraint |
| --- | --- | --- |
| Rolling | Slow, mixed-version throughout | Strictest - bidirectional compatibility |
| Blue-green | **Seconds** | Same, plus the switch-back hazard |
| Canary | Fast for the canary | Same, for longer |
| Dark launch | Instant | Loosest (if no writes) |

**Rolling deployment needs backwards AND forwards compatibility simultaneously** (Q31). And rollback needs the *old* code to read what the *new* code wrote - **the data does not roll back**.

**Expand-migrate-contract** (Q177):

1. Add the new structure (nullable, no rewrite, `CREATE INDEX CONCURRENTLY`)
2. Deploy: write both, read old ← **rollback point**
3. Backfill in throttled batches; verify zero mismatches
4. Deploy: read new, write both ← still safe
5. Soak (days)
6. Deploy: write new only ← **point of no return**
7. Add constraints, soak, drop the old column

**Column rename across two services**: 10 steps, rollback point after the owner switches its read (Q178).

**Message schema, additive change**: deploy **consumers first**, then producers. For a removal, **producers first** (Q179).

**Feature flag expiry**: release and experiment flags **must** expire; ops (kill switch) and permission flags are permanent (Q175).

**Flag disagreeing across services**: evaluate **once at the edge and propagate the decision** (Q176).

## API versioning decision table

| Approach | Use when |
| --- | --- |
| **No version, additive only** | **Default.** Requires tolerant readers and a breaking-change linter |
| URI path `/v2/` | A genuine breaking change, external consumers, cache-friendliness matters |
| Media type | Per-resource granularity needed and tooling supports it |
| Header | URIs must stay stable; accept the invisibility |

**Retiring a version**: announce with `Sunset`/`Deprecation` headers → instrument per-version per-consumer usage → contact consumers individually → **brownout** on announced dates → retire (Q27).

**Protobuf**: never reuse a tag number; always `reserved`; `buf breaking` in CI. Renaming a field is wire-safe (except JSON transcoding); changing its type is not (Q24).

## Strangler fig migration order

1. **Observability and instrumentation first** - count calls to every legacy code path
2. **Characterization tests** on what you will touch
3. **Facade in front, 100% still to the monolith** - prove the router before it matters
4. **Modularize in place**: enforced module boundaries, **separate schemas, no cross-schema joins**
5. **Extract a peripheral pathfinder** to build the platform
6. Per slice: **code → traffic → data** (data last, it is the irreversible step) (Q224)
7. **Parallel run** with comparison for anything with complex legacy rules
8. **Delete the legacy path.** A slice that is not deleted is not done (Q220)

**Data migration risk order**: CDC + gradual cutover < one-shot with downtime < **dual write** (Q226).

**Both systems writing the same data** (Q221), best to worst: avoid (single writer) → partition the writes → one writer at a time per entity → DB-level conflict prevention → dual write → bidirectional sync.

## Multi-tenancy

| Model | Isolation | Cost | Noisy neighbour |
| --- | --- | --- | --- |
| Silo (dedicated) | Strongest | Highest, linear | None |
| Bridge (shared compute, isolated data) | Good | Moderate; N migrations | Partial |
| Pool (shared everything) | Weakest | Lowest | Worst |

**"Every query includes tenant_id" is not isolation.** Enforce with row-level security, tenant from the **verified token only**, tenant-prefixed cache/storage/index keys, and generated cross-tenant access tests. Missing tenant context **fails closed** (Q166).

## Security

**Edge auth + internal trust** assumes the network is a boundary. **End-to-end propagation** assumes any service may be compromised.

`X-User-Id` header internally = forgeable. SSRF, one compromised service, or one bypassed gateway path = total impersonation, with a worthless audit trail. Acceptable only under mTLS workload identity, or if signed (Q156).

**Token exchange (RFC 8693)** at every hop: audience-restricted, scope-narrowed, short-lived, with an `act` claim recording delegation (Q157).

**Bootstrapping identity**: you cannot distribute a secret to prove identity. **The platform attests** - projected service account token → TokenReview → short-lived SVID (Q135, Q159).

**Secrets ranking** (worst → best): env var static → secret manager static → **dynamic secrets** → **workload identity (no secret at all)** (Q165).

**CA rotation order** (Q160): new CA → **distribute both in the trust bundle and verify** → switch issuance → wait a full leaf lifetime → remove the old CA → revoke. Reversing steps 2 and 3 breaks everything at once.

## Testing

**Honeycomb, not pyramid**: few unit, **many service/component tests** (real DB via Testcontainers, external deps stubbed from published contracts), contract tests, very few E2E (Q201).

**`can-i-deploy` is the coordination mechanism.** It replaces the release train, the integration environment and the coordination meeting with a broker query (Q204).

**Contracts verify compatibility, not correctness.** Pence-to-pounds passes every contract test (Q205).

**Never `Thread.sleep`** - Awaitility with a generous timeout and a short poll, a controlled `Clock`, or a deterministic scheduler (Q206).

**Mandatory test cases per handler** (Q207): exact duplicate, duplicate after delay, duplicate on another instance, **concurrent duplicates**, crash after effect before ack, retry classification, DLQ on permanent failure.

**3% flaky is worse than 30%** - 30% is a crisis and gets fixed; 3% normalizes "just re-run", which destroys the signal for real failures (Q210).

## Fast answers to trick questions

| Question | Answer |
| --- | --- |
| Exactly-once delivery? | Does not exist. Exactly-once *effect*, via consumer idempotency |
| Timeout means the write failed? | **No - unknown.** Query by idempotency key |
| Circuit breaker on a slow dependency? | Does nothing. Configure a **slow-call rate** + bulkhead |
| Redis distributed lock for correctness? | No. No fencing token. Use a unique constraint or a consensus store |
| Empty-list fallback? | Distinguish "no data" from "could not get data". Never fall back on writes or destructive jobs |
| Readiness checks the DB? | All instances fail together = total outage |
| More partitions fixes a hot key? | No - the key still hashes to one partition |
| Average the p99s? | Meaningless. Aggregate histogram buckets |
| Sampled at 1%, no errors in traces? | You kept 1% of the errors too. Tail-sample on outcome |
| Adding a replica always helps? | Cold cache, downstream contention, coherency cost |
| Contract tests passed, prod broke? | Semantics, provider state fidelity, or environment |
| `updated_at` for conflict resolution? | Clock skew + silently discards concurrent writes |
| Async increases capacity? | No - it changes the cost of *waiting*. The bottleneck is unchanged |
| Two services always change together? | Prove it with change-coupling from git before recommending anything |

## Answer shaping

**Four-layer technical answer**: direct answer → mechanism → trade-off → experience hook.

**CIDER for scenarios**: Clarify → Isolate → Decide → Execute → **Reflect** (what you monitor and prevent - the step people skip).

**STAR-L for behavioural**: Situation, Task, Action, Result (**quantified**), Learning.

**Timing**: technical answers 60-90 seconds. Scenarios under 4 minutes. Design exercises: spend the first 2 minutes clarifying, and never open with a diagram.

**Always name**: what you would *not* build, the trade-off you are accepting, and what you would monitor afterwards.
